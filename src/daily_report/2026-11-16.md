### 1. [ggml-org/ggml](https://github.com/ggml-org/ggml) · ⭐ 15,845 · C++ · 日榜第 8（回榜，02-21 曾列第 8）· v1.0.0（11-13 08:34 UTC）· 评分 6.9

llama.cpp 底下的张量库，11-13 发出第一个稳定版，把「张量运算库」也变成一个可以被长期依赖的契约。

要点：v1.0.0 砍掉全部废弃公开 API 与遗留的 `DIAG_MASK` 算子，RPC 协议升到 v9，遇到不兼容的 peer 直接拒绝握手；新增 `ggml_rope_set_truncate` / `ggml_rope_get_truncate` 用来控制 YaRN 修正边界的取整，补上 `TRI` 的反向传播；后端侧给 CUDA 补了 2–24 批次的 few-row MMQ 与 BF16 few-row matmul（MMVF）、OCP FP8 支持与 MMQ 里融合 GLU 的 NVFP4 gate/up matmul，Metal 上加 MoE 融合，Vulkan 加 prefill 用的 FlashAttention 路径，SYCL 加 device 端 MoE 调度器，OpenCL 拆出 Adreno 的 FlashAttention，另加新 WebGPU kernel 与更多 Hexagon 算子；调度器开始跳过上传没人读的输入，MoE cache 允许在 CPU 上先算一部分 cache miss 再异步拷回。仓库本身是纯 C/C++ 无依赖实现，跨 x86 / ARM / RISC-V / LoongArch / PowerPC / s390x / WebAssembly，SIMD 内核覆盖 x86、ARM、RISC-V，支持 2–8 位整数量化以及 MXFP4、NVFP4 微缩放格式，运行时零内存分配，MIT 许可。

**它和同门的 llama.cpp v1.0.0 相隔 1 小时 46 分先后发布，这个间隔本身就是一句设计说明**：引擎先冻结接口，底座再冻结接口。llama.cpp 的 v1.0.0 在 11-13 10:20 UTC 发布，ggml 的在 08:34——先给推理引擎一个可依赖的 API 边界，再把张量层也纳入同一套版本纪律。而 11-15 日榜上出现的是 ggml 这个底座（llama.cpp 当天并未上榜），也说明今天被看见的不是某个模型，是它下面那层。对所有在本地跑模型的人来说，今天该关注的不是「1.0 又多了几个 kernel」，而是**接口不再变**这件事本身。

### 3. [NVIDIA/SkillEvaluator](https://github.com/NVIDIA/SkillEvaluator) · ⭐ 1,465 · Python · 日榜第 12（本地 420 天快照首次上榜）· v0.9.0（11-13）· 评分 6.8

NVIDIA 官方的 Agent 技能评测框架：质量门禁 + 语义重叠检测 + 合成评测集 + 真机行为评测。

要点：三条路径同一套 CLI——`pip install skillevaluator` 后 `skillevaluator validate ./my-skill --tiers 1` 可在不用任何 API key 的情况下跑完第一层质量检查（自带确定性的 `text-analyzer`）；`skillevaluator ci init` 会开一个 setup PR，把技能检查挂进每次 pull request，GitLab 侧直接用 `ci/bundles/0.9.0` 里的模板；还可以把仓库里的 SkillEvaluator 技能本身装进 Claude Code 或 Codex（`npx skills add NVIDIA/SkillEvaluator`），然后直接问 Agent「我这个 skill 行不行」。需要 NVIDIA Build API key 时可换成模型打分与反馈。分层的核心能力包括：带质量门禁的静态检查、跨技能的语义重叠检测、合成评测数据集生成，以及「上线跑一次、看技能到底改变了 Agent 行为多少」的 live agent evaluation。它属于 NVIDIA Verified Skills 流水线（github.com/NVIDIA/skills），论文见 arXiv 2608.20614，文档在 docs.nvidia.com/skills/skillevaluator，Apache-2.0 许可，支持 Python 3.12 / 3.13 / 3.14。

**NVIDIA 出手的位置很讲究：不是再造一个技能框架，而是给别人的技能框架做质检。** 仓库 2026-06-24 才建，v0.9.0 是 11-13 刚发的，今天第一次进本地 420 天的日榜快照——星数只有 1,465，是今天榜单上星最少的一条，但它是榜单上唯一一家大厂做的「技能质检」基础设施。技能数量在涨，技能质量却没有统一的验收方式，NVIDIA 填的正是这个位置。

一次安静的默认值切换，成本翻了 15 倍。

要点：`Agent(task)` 与 `ChatBrowserUse()` 的默认模型从 `bu-fast` 换成浏览器网关上的 **BU 4.0**；官方在发版说明里直接写明了代价——BU 4.0 的 token 单价是 `bu-fast` 的 15 倍（每百万输入 / 输出 token $1.80 / $9.00 对 $0.12 / $0.60），默认还从 medium reasoning 升到 high reasoning，一个短测试任务的花费从 $0.0014 变成 $0.022；要压成本就显式传 `llm='bu-4.0-mini'`，要跑最难的任务传 `'bu-4.0-pro'`，想维持旧价格得传 `llm='bu-fast'`；首次运行没有 key 时会打开 Browser Use 登录页、审批后继续，云端浏览器会打印实时观看链接；Judge 的判断被约束在这次运行实际观测到的内容上。

**默认值就是政策**：浏览器 Agent 的默认模型从「便宜快」换成「贵而准」，等于官方替所有用户做了一次成本与效果的取舍，而且方向是往上。这一点对正在用 browser-use 跑自动化的人比任何新功能都重要——今天的账单可能比昨天高一个数量级。

### 10. [meta/zstd](https://github.com/meta/zstd) · ⭐ 28,255
