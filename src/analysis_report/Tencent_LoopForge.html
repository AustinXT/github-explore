GitHub: https://github.com/Tencent/LoopForge

一句话总结

腾讯把内部用了数年的 AI 编码 Agent 编排平台（内部代号 AgentFlow）整体开源——它不训模型、不自带 Agent，而是把 CodeBuddy、Codex、Claude Code、Cursor 等十种编码 CLI 装进一张可编辑的 SOP 图：确定性的 build/test/lint 走脚本节点、需要判断力的走 Agent 节点、关键决策停在人工闸门，全程留下可审计的痕迹。

值得关注的理由

  1. 它公开了别人通常闭门自用的那部分：多 Agent 编排赛道拥挤到几十个玩家，但「可插拔编码 CLI + 确定性脚本节点 + 强制人工闸门 + 全链路审计 + 自托管」这五项同时成立的极少。多数竞品只占其中一两项——终端编排器（Claude Squad / dmux）有隔离没门禁，看板面板（Yao）有界面没流程，SDK 框架（MetaGPT）有概念没平台。
  2. 「写代码的 Agent 永远不是评审的那个」这条强制职责分离，是本轮 AI 编码里最值得抄的一条设计：把 Agent 的输出限制成一个受约束的裁决（pass / rework / fail / human），由确定性引擎负责路由到重试、打回上游、终止还是转人工——AI 意图与流程执行之间隔了一层窄接口。
  3. 工程细节的密度远超同级项目：Go 内部零 unwrap、840 个测试文件、85% 覆盖率闸门、路由覆盖率闸门、CI 配置本身也被测试、数据库租约 + generation 栅栏、数据库时钟做心跳时基、手写 SQL 迁移归档、docs/validation.md 里把「111 passed, 1 failed」照写不改——这份「诚实」在 0.4.x 阶段的开源项目里相当罕见。

作者视角：为什么存在这个项目

创始人/作者背景

作者不是独立开发者，而是腾讯官方组织账号（10.6 年历史、15,310 粉丝、314 个公开仓库），背后是腾讯内部研发效能 / 云业务团队。账号下有 ncnn（24k star）、puerts（6.2k star）、libpag、cherry-markdown 等成熟项目背书，LoopForge 在其最近活跃仓库中排第 2——是当前新宠，但绝非唯一焦点。

最有说服力的证据不在 README 而在 docs/open-source-scope.md：README 直呼内部旧名 AgentFlow（Go module 名至今仍是 agentflow，AGENTFLOW_ 环境变量前缀被刻意保留以「减少合并冲突」）；开源范围声明逐项剥离了「无内置员工白名单」「不推断企业关联身份」「Git 提交身份使用本地账号名 + 不可投递的 LoopForge 邮箱」「TAPD 导入/推送等组织专用 tracker 协议保留为可选兼容代码且 Web 入口默认隐藏」。这是从企业内部版剥壳开源的典型痕迹，而不是「为了开源而写一个 Demo」。

问题判断

作者看到的不是「AI 写代码不够强」，而是「写代码的强度已经够了，交接才是瓶颈」。README 的一句话就是全部立论："Code was never the bottleneck. The handoff is."

落到具体场景：让 coding agent 去「修个 bug」，结果完全取决于那次运行——可能跳过计划、忘记跑测试、自审自己的代码、半途停下而无人察觉。对 demo 无妨，对团队交付不可接受。所以真正稀缺的不是更强的 agent，而是流程层与审计层。

时机也讲得通：2025–2026 年 coding agent 从「能写代码」跨到「能交付」的临界点上，单任务质量不再是瓶颈，瓶颈转移到多任务编排与验收——团队第一次有了「必须买一套流程基础设施」的动机。腾讯内部先用真需求把它磨出来（据腾讯灯塔官方复盘，内部服务 20+ 业务、每月 200+ 需求工单自动产出 MR；该数字由利益相关方撰写，应打折看），然后才把壳剥掉开源。

解法哲学

作者的选择比 feature 列表更能说明问题：

  • 「No AI where AI is not needed」。SOP 有五类节点：Agent 角色、确定性 Script（build / test / lint / report）、Human gate、Sub-SOP、Preview build。Script 节点与 Agent 节点平级——能被脚本判定的事，绝不交给大模型。这是把成本与稳定性同时压下来的关键取舍。
  • 「Human on the loop」而非「in the loop」。人不是被 Agent 反复询问的下属，而是流程里一个可插入的节点。人工闸门有三种动作：批准 / 补充上下文 / 打回指定步骤（RejectTo）。第三种动作是精髓——人可以精准地把流程推回上游某一步，而不是从头再来。
  • 机制管权限，prompt 管不了。多 Agent 最危险的三件事（越权、乱装依赖、串改目录）被做成机制而非提示词：权限三档（请求批准 / 帮我批准 / 完全放行）、网络出口白名单、目录挂载可写与只读分离。
  • 跨厂商中立。十种 CLI 均为一等执行器，腾讯自家 CodeBuddy 只是默认选项而非绑定；Topics 同时挂 codebuddy / codex / claude-code / cursor，是明确表态。
  • 明确不做的事：不做本地模型运行器；不做多租户隔离（README 明说「默认适配可信团队，不是不可信多租户」，因为 Docker socket 访问等于宿主 daemon 控制权）；不做「整份重写 SOP」的自进化。

战略图景

LoopForge 是基础设施而非终点产品。AGENTS.md 把工程治理写成硬约束（repo 层一领域一 Repo、handler 层一领域一 handler、禁止代码内迁移与 seed、迁移一律手写 SQL）并附「历史整改记录」，说明它被当作需长期演进的平台底座。

docs/open-source-scope.md 的关键句是「Behavior and execution are shared with master; operator assets, credentials and private integrations are deployment data」——行为与内部版一致，只是数据分离。MIT 许可、GHCR 公开发布、无企业版功能墙、无遥测上报、无 SaaS 端。这是 genuinely open，不是 open-core；商业化意图在仓库里看不到痕迹。

核心价值提炼

创新之处

按新颖度 × 实用性排序：

  1. 门禁作为可编程对象（Gate-as-Value） — 新颖度 4/5 · 实用性 5/5 · 可迁移性 5/5 门禁不是硬编码的 if，而是带 Mode / Stage / OnFailure / ExecutionScope 的值对象：可在 SOP 画布上编辑、可被角色复用（AgentDefinition.Verification）、可被 runeval 增删（upsert_gate / remove_gate）。三种判分主体（脚本命令 / Agent 判定 / 主机查询，如 MR 校验）与四种失败响应（loop / reject / fail / human）落在同一张表上。任何「AI 参与的流水线」都能搬这套。

  2. 判定与执行分离：Agent 只产出裁决，引擎负责路由 — 4/5 · 5/5 · 5/5 Agent 通过 submit_gate_result MCP 工具提交四种决策之一（pass / rework / fail / human）加一段理由，schema 严格校验（reason 必填、≤4000 字符、findings ≤50 条）。引擎把它映射成重试、打回上游、终止或转人工。Agent 不能改图、不能改流程，只能在受控词汇表里选一个裁决——这是「AI 意图 → 引擎动作」的窄接口，比让 Agent 直接调工具安全得多。

  3. 返工预算耗尽 → 停人工闸门而非标失败 — 4/5 · 4/5 · 4/5 节点的 RejectTo 重试预算用尽时，代码显式把状态置为 waiting_approval，文案写「返工预算耗尽，等待人工决策」，并解释「批准 = 接受当前上游结果继续下游」。把「能力到顶」与「基础设施故障」在失败语义上分开——前者不是错误，是需要人决策的状态。

  4. 闸门命令的语义修正层（bindVerificationCommand） — 5/5 · 5/5 · 4/5 引擎读懂并修正人写的断言命令：git diff --quiet 自动排除本节点声明的交付物路径（免得把上一次的 fix-plan.md 当成脏文件）；裸 grep / rg 忘写文件名时自动补上产物路径（裸 grep 读空 stdin 必然失败）；ALL_GREEN / NEED_HUMAN 自动加正则锚点。这是全仓库最「小而狠」的工程细节——它让「让人手写 CI 断言」这件事真正可用。

  5. 锚定判分 grep（anchorVerdictGrep） — 4/5 · 5/5 · 5/5 Agent 的报告常写「ALL_GREEN=true，但本次不适用，因为它……」——未锚定的 grep 会把解释当结论，于是人工闸门在一个根本没有结论的 run 上停住。修法是把匹配改写成要求结论行独占一行。这是 LLM + 文本门禁场景里最容易踩、也最难 debug 的坑。

  6. 零宽字符去活化（InertCLIText） — 5/5 · 3/5 · 3/5 CodeBuddy CLI 渲染 Skill 文本时，!`cmd` 会在 shell 执行、@path 会内联宿主文件。控制面的 CLI 虽然禁用了 Bash，Skill 文本仍可能通过渲染路径触达宿主。解法是在反引号命令与「行首或空白后的 @」之间插入零宽空格作为断点，同时精确复刻目标 CLI 自己的 @ 解析规则（代码块内的 @types/node 不动）。代价是文本「视觉上一样，字符上不同」，换来无需信任 Skill 作者即可安全渲染。

  7. ExecutionScope：脚本作用域与物理布局解耦 — 4/5 · 5/5 · 5/5 门禁命令不需要知道自己在一个仓库还是多个仓库的 checkout 里跑。引擎注入 AGENTFLOW_EXECUTION_SCOPE、AGENTFLOW_REPOSITORY_ID/DIR、AGENTFLOW_WORK_BRANCH、AGENTFLOW_BASE_BRANCH（仓库级）或 AGENTFLOW_WORK_BRANCHES（run 级，dir<TAB>work branch<TAB>target branch），脚本自己读环境变量决定行为。多仓库工作流与 monorepo 门禁直接受益。

  8. 受限流程补丁（Constrained Patch Envelope） — 3/5 · 4/5 · 5/5 runeval 外环可以让 LLM 改流程，但只能在四种 action（update_node / upsert_gate / remove_gate / append_task_prompt）+ 四个整数字段（maxAttempts / maxReworks / onFailure / retryStrategy）的白名单内改；upsert_gate 强制 Mode=command、Required=true；HTTP 层要求带非空 recommendationIds，逐条 Applyable() 判定后必须由人勾选才落库，状态从 pending 变 applied。评测 prompt 还明确禁止「整份重写 SOP / 改边 / 删节点」。这是把「AI 自优化」从口号拉回工程的关键约束集。

  9. 统一 Observability Spec + Adapter Descriptor — 3/5 · 5/5 · 5/5 十种 CLI 的异构输出被归一成 13 类 telemetry × 3 phase 的统一事件流，每个 adapter 声明自己的能力矩阵与 RawEventPolicy（归一化后丢弃原始事件）。runeval、成本核算、节点检查器全部建立在这层之上。

  10. 数据库时钟作为心跳与租约的唯一时基 — 3/5 · 5/5 · 4/5 心跳年龄与租约到期都按打戳它的数据库时钟计算，而不是各副本本地时钟，彻底消除跨副本时钟偏移导致的「误杀活着的 turn」与「吊死已死的 turn」。多副本分布式任务系统的通用解法。

可复用的模式与技巧

以下模式与具体业务无关，可以直接搬：

  1. 生成式裁决 → 受控动作映射：把 LLM 的自由文本裁决压到有限枚举，再用确定性代码映射成引擎动作；映射不成立时降级为安全终态，而不是给出一个无法执行的指令。
  2. 失败语义三分（可重试 / 能力到顶 / 硬失败）：把「预算耗尽」从 failed 里拆出来单独走人工闸门。
  3. 结果分代落盘（attempt-N.json）：需要持久化的判定按 attempt 分代存放，杜绝陈旧结果污染新尝试。
  4. 事件流归一化 + adapter 能力声明：为每种异构输入源写适配器，输出统一事件 schema，并声明各自能力矩阵。
  5. 窄键锁（keyed locks with refcount）：并行化一切，只对真正互斥的三类资源加锁，锁条目引用计数用完即删不泄漏 mutex。
  6. 独占写栅栏（generation + attempt 三重校验）：迟到结果必须同时通过「租约归属」「节点仍活跃」「attempt 匹配」三重校验才允许落库，且成功路径有意放宽 attempt 校验——通过了门禁的活 agent 不该因重试 bump 了 attempt 而被丢弃。
  7. 命令语义修正层：引擎读懂并修正用户写的断言命令（补路径、加锚点、加排除）。
  8. 零宽字符去活化：用不可见字符阻断不可信文本在 CLI 渲染时的执行通道。
  9. 数据库时钟作为唯一时基：心跳与租约一律按数据库打戳时间计算。
  10. 受限补丁信封：允许 LLM 改流程但限制在白名单内，且默认 pending 需人工确认。
  11. 显式 SQL 迁移，禁止代码内自愈：生产 schema 变化全部手写 SQL 归档，代码只做连接与增量 DDL。
  12. 判分锚定：让 LLM 输出的结论在语法层独占一行，避免叙述被误判为结论。

关键设计决策

  1. 并行分支用三把窄键锁，而不是串行化整条 run - 问题：早期把整个 run 串行化就没有并行；但完全放开会撞车——同一角色的两个节点共享 .agentflow/<agent> 控制目录、private home、gate MCP 配置。 - 方案：keyedLocks（引用计数，条目用完即删）三把键——node\x00run\x00node（一次执行）、agent\x00workspaceOwner\x00agent（一次 CLI 调用）、pool\x00run（一次执行机绑定）。其余准备/检出/物化在 runEnvironment.nodeMu 下，且只在准备阶段持锁，之后并行。 - Trade-off：需要精确判断「什么必须互斥」；换来并行分支真并行。

  2. 门禁结果用文件契约，而不是进程返回值 - 问题：Agent 跑在一个可能随时被销毁的容器里，判定结果必须落在可持久化的地方。 - 方案：submit_gate_result 经 MCP 写入 .agentflow/gate-results/<node>/attempt-N.json，引擎按 attempt 分代读取；若该 attempt 没有有效结果，注入「缺失门禁结果」标记并要求 agent 立即提交。 - Trade-off：需要处理「上次 attempt 的陈旧结果」这个真实存在的坑（所以路径带 attempt 号）；换来容器销毁不丢判定。

  3. run 状态跨进程用数据库租约 + generation 栅栏 - 问题：多实例共享一个 run，进程重启后 run 停在 live 状态怎么办？ - 方案：TryAcquireRunLease / RenewRunLease + OwnerInstanceID + Generation + LeaseUntil；ResumeInterruptedRuns 把上次进程遗留的 in-flight 节点重置为 pending 继续，停在人工闸门的 run 不动（人工仍可 Approve / Retry 恢复）。 - Trade-off：数据库成为强依赖；换来进程崩溃后 run 可恢复。

  4. 工作区 checkpoint 排除凭据，且「存不下就不授权删除」 - 问题：沙箱工作区要被回收，但代码改动不能丢；同时 checkpoint 不能把 API key 和 node_modules 打包带走。 - 方案：checkpointExcludedNames 排除 .agentflow（恢复时绝不允许出现）、node_modules、.cache、__pycache__ 等；归档上限 12 MiB，WorkspaceCheckpointArchiveMaxBytes = 512 MiB 用 4 MiB 分块 + 磁盘流式传输，绝不塞进一个 JSON 值或数据库单元。注释明写「A bounded archive that cannot be saved must never authorize workspace deletion」。 - Trade-off：大工作区存不下就恢复不了；换来凭据不外泄 + 存储不爆。

  5. 角色定义复用为「SOP 节点」与「对话子 Agent」两种形态 - 问题：若规划/实现/评审/测试各写一份 prompt 模板，SOP 里和聊天里行为不一致。 - 方案：AgentDefinition 同时携带 prompt / rules / skills / mcpServers / hooks / artifactOutputs / verification / loop policy，既可作 SOP 节点绑定，也可作 chat 里的 subagent 被 dispatch。 - Trade-off：一份定义要同时满足两种调用场景，prompt 需要额外包装。

  6. 超过 argv 上限的 prompt 自动改走 stdin - 问题：Linux 单个 argv 参数超过 MAX_ARG_STRLEN（128 KiB）会 E2BIG，CLI 根本起不来。 - 方案：maxArgvPromptBytes = 96 << 10 留余量；PromptOnStdin 只改写以 -- 结尾且末位是 prompt 的命令，把 prompt 移到 stdin 并保留 -- 分隔符。 - Trade-off：条件判断有点绕；换来「长 prompt 不炸」。

  7. Store 上禁止新增领域方法 - 问题：Go 项目里 Store 极易腐化成 God Object。 - 方案：AGENTS.md 定为硬约束——Store 只做组合与生命周期，跨领域视图一律降级进领域 Repo，并附「历史整改记录」说明这条规则真被执行过。

差异化护城河

信任护城河（最强） + 技术护城河（中），生态护城河弱。

  • 信任护城河来自「机制管权限」：权限三档、网络出口白名单、目录读写分离、MCP 凭据 actor-scoped、密钥掩码、敏感变量日志脱敏、gitleaks 密钥扫描、govulncheck 零漏洞、86 个依赖许可核验、迁移全部手写 SQL 可审计、.agentflow 在 checkpoint 恢复时绝不允许出现。这些是「敢放进企业内网跑」的硬门槛，也是竞品普遍不做或做得不细的部分。
  • 技术护城河在于十种 CLI 归一化 + 可观测性契约 + 门禁语义这层适配工作量（Go 5 万行自研代码、51 个运行时依赖）。但要说清楚：这是工程量壁垒，不是算法壁垒。
  • 生态护城河弱：MIT 开源、GHCR 分发、无插件市场、无第三方 SOP 生态。

竞争风险

  1. 最高风险：superplane 的工程成熟度追赶。superplane 已经具备「平台」的形，只需补一层 SOP DAG 与人工闸门就能对标，而它的 star 数近 LoopForge 两倍、生产部署踩坑记录更厚。
  2. 第二风险：coding agent 厂商自建。Anthropic、OpenAI 都在往编排层走，若某家把「多 CLI 中立编排 + 审批门禁」做进官方产品，LoopForge 最大的差异化——中立性——瞬间归零。
  3. 第三风险：执行器脆性。人工审批是 LoopForge 的核心卖点，而它在「某个 CLI 没装好 / 环境有缺」的失败路径上恰恰最脆（详见风险节）。
  4. 概念本身不构成壁垒：「SOP 编排」这个概念 MetaGPT 早在 2023 年就提出来了。LoopForge 赢在把它做成了有审计、有权限模型、有沙箱的平台，而不是发明了这个词。

生态定位

LoopForge 是多 Agent 时代的 CI/CD 与门禁层。

如果 coding agent 之于软件开发相当于编译器，那 LoopForge 想做的是 CI/CD 流水线 + 审批工作台 + 审计日志——只不过流水线的每个 stage 现在是一个 agent。这个类比相当贴切：CI 系统的价值从来不在「跑测试」本身，而在于它是团队公认的、可追溯的、可强制执行的流程载体。LoopForge 试图把这件事在 Agent 时代重做一遍。

它不与 agent 竞争——它甚至不自带 agent——而是给十种 agent 提供一个共同的、可审批、可复盘的编排外壳。这个位置在生态上很正，但也意味着它的价值完全依赖于「SOP 图 + 门禁」这件事本身被行业广泛接受。

套利机会分析

  • 信息差：star 数已被推广期红利透支（11/12 451 → 11/21 5273），追高没有空间。但内容稀缺性仍在——SOP DAG 引擎、职责分离、runeval 六维评分、权限三档这些细节，别人通常闭门自用，而这里被完整开源并写进了 73,490 行的 design.md（中文）。读者姿势应是「拆解 SOP 引擎与 runeval 的设计，而非把它当产品选型」。
  • 技术借鉴：可迁移性最高的四件事——① 门禁作为可编程对象；② 判定与执行分离的窄接口；③ 锚定判分 grep 与命令语义修正层（任何 LLM + CI 门禁场景都会踩）；④ 数据库租约 + generation 栅栏 + 数据库时钟时基（多副本分布式任务的通用配方）。这四样都不依赖腾讯、也不依赖 Agent 编排语境。
  • 生态位：填补「个人 agent 编排器」与「企业研发效能平台」之间的缝隙——前者没门禁没审计，后者不开源闭门自用。
  • 趋势判断：符合「AI 从辅助编码走向可交付工程」的方向，且有后发优势——它站在 2026 年的模型能力之上，而不是 2023 年的。风险则在于它站在「十种 CLI」之上，而 CLI 层的变动频率远高于编排层。

风险与不足

  1. 多执行器是最大的结构性负债。十种 CLI × 每种的 hook 格式 / 凭据格式 / 模型目录 / 思考强度档位 / MCP 配置格式 = 组合爆炸。代码里 InstallConversationApproval 已是一个 100+ 行的 switch：Kimi 只在 exit code 2 时拦截（|| exit 2），Codex 要 -c features.hooks=true 加内联 TOML，Cursor 要 failClosed: true，Antigravity 要写 .gemini/config/hooks.json，DeepSeek 要生成 patch 文件。每加一种 CLI 就多一条失败路径，而核心卖点（人工审批）在这些路径上恰恰最脆。
  2. Issue 已经证实了这个脆性：#49 报告 Classic CodeBuddy 在未装 PyYAML 时忽略 auto_mode: false，人工闸门被静默跳过；#892 报告 Docker 部署首次使用 Claude Code 失败（CLI 从 npm 安装超时）。这是结构性问题，不是孤立 bug。
  3. 状态机标识符不稳定。#1079 暴露审批闸门等待中的 run 被绑定在旧容器 hostname 上，容器重建后永久阻塞。代码里 workspaceLost / workspaceBlocked / foreignWorkspaceBind 一整套逻辑在处理「绑定的机器没了」，说明这不是罕见路径而是常态。而「Pause, retry a failed step, or rerun from any node」这个核心承诺，前提正是基础设施层的标识符稳定——这是当前最脆的一层。
  4. 「自进化」闭环缺数据底座。#170 报告 SOP 定义本身会丢；#460 把「成果归因」列为待办。归因是 runeval 评分与流程补丁的输入前提——没有可靠归因，「跑完后自动改写自身 SOP」就只是叙事。外部分析给出的边界澄清也与此一致：补丁禁止整份重写 SOP、禁止改节点连线、禁止删节点，且默认 pending 状态必须人工选择才生效。
  5. 规模与项目阶段不匹配。54.8 万行、30 个 Go 子包、3070 个文件，对一个 0.4.x、92% 提交集中在最近 30 天、23 名贡献者的项目来说体量偏重。最热的文件是 docs/deployment.md（改了 44 次）——运维债集中位置的直接信号。另有 web/vscode-web 里 60MB vendored 发行物，贡献了 722 次「修改」的统计噪声。
  6. 前置依赖重，采纳成本是真门槛。MySQL + Docker + Docker socket + 十种 CLI 之一 + Git 授权 + 模型 key。scripts/install.sh 要处理 apt/dnf/yum、x86_64/arm64、镜像源、npm 源、Python 3 引导——脚本的复杂度本身就是产品复杂度的镜像。这是与 Claude Squad 一类工具最本质的差距。
  7. 「开源 dump」而非「社区共建」的持续性存疑。375 个 commit 里 346 个集中在 30 天内，Refactor 占 35%（feature 16% ≈ fix 17%）——主体是把腾讯内部代码整理成可公开形态。PR 队列积压 196 条多于 89 个 issue，说明外部贡献者在排队而维护带宽有限。未来 1–2 个月的社区参与密度是真正的试金石。
  8. License 元数据不一致。GitHub 侧标 Other，仓库内正文是 MIT，商用前需核对。
  9. 可观测性承诺与实现存在落差。#1118 报告会话开始后运行时选择器整块消失，用户无法确认当前用的是哪个 CLI——这直接命中多执行器架构最核心的可解释性痛点。

行动建议

  • 如果你要用它：
  • 适合：有重复交付需求、需要正式审批与可追溯记录、且运行在可信私有网络的研发团队（自建开发效能平台的团队尤其对口）。
  • 不适合：个人开发者、偶尔的编程辅助、需要公网多租户的场景、要求零运维的场景。外部评测的判断可以参考——「适合需要重复交付、正式审批、可追溯的团队，不适合轻量终端助手」。
  • 落地顺序建议：先跑通一条最简单的 Script + Human gate 的 SOP（demo project 里就有模板），验证审批体验，再逐步引入多角色与 Agent 节点；不要一上来就上多 Agent 编排。
  • 升级前必看：15 个 release 只覆盖 375 个 commit，平均每个 release 含 25 个 commit、跨数百个文件的变更——变更面很大，务必读 docs/deployment.md 里「升级必须手动跑一次的脚本」清单（migrations/ 下的手写 SQL）。

  • 务必核对 LICENSE 实际协议，以及各 CLI 的凭据配置（官方文档化不足，需自行翻各家文档）。

  • 如果你要学它（按性价比排序）： 1. internal/engine/ —— SOP DAG 引擎：节点类型、readyNodes 依赖求值、并行分支、shouldCommitNodeOutcome 独占写栅栏 2. internal/runtime/ —— 沙箱与权限模型：权限三档、网络出口白名单、挂载读写分离、InertCLIText 零宽字符去活化 3. internal/httpapi/ —— 门禁结果接入与 applyGateResult 的降级路由；bindVerificationCommand 与 anchorVerdictGrep 的命令语义修正层 4. internal/runner/daemon.go —— 执行器调度与 keyedLocks 窄键锁 5. AGENTS.md —— 分层硬约束与 Store 禁止新增领域方法 6. docs/open-source-scope.md + docs/validation.md —— 如何写一份诚实的开源范围声明与验证记录

  • 如果你要 fork 它：

  • 收敛执行器数量：从 2–3 种主流 CLI 起步，把 InstallConversationApproval 的复杂度砍下来，把人工闸门在故障路径上的脆性一并解决——这是当前最高价值的改进方向。
  • 修标识符稳定性：#1079 类问题的正解是让 run 与 workspace 的绑定不依赖容器 hostname（改用稳定的 workspace UUID + 重建时的重绑定），这是「可恢复」承诺的地基。
  • 补成果归因：把「哪个角色/节点贡献了这单交付」做成一等数据实体，runeval 外环才有输入，自进化叙事才从口号变闭环。
  • 轻量化部署：把 MySQL 依赖与 Docker socket 需求做成可选档位（SQLite + 进程内沙箱），能直接吃掉与 Claude Squad 的采纳成本差距。
  • SOP 定义持久化：#170 暴露的配置丢失问题，参照它自己「配置即代码 + 版本化快照（DefinitionRevision 不可变快照 + 发布态）」的思路加固。
