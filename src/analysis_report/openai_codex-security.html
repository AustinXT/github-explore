GitHub: https://github.com/openai/codex-security

一句话总结

OpenAI 把内部的 AppSec 产品 Aardvark 开源成一套「扫描 → 调查 → 验证 → 修复」的 LLM 驱动安全 agent 流水线，真正的技术资产不是扫描能力本身，而是那套让非确定性 AI 产物变得可审计、可回归、可去重的契约体系。

值得关注的理由

  • 首个公开全栈的 LLM 安全 agent 实现：Claude Code Security 架构最同构但不开源，Codex Security 是目前唯一能逐行读源码的同类——scan-contract.md、shared-hard-rules.md、20 份 reference 契约构成了罕见的「AI 安全工具工程」公开样本
  • 给非确定性 agent 造确定性回归：evals/ 五套评测用「布局分离 + 三信号分离 + 原始分保留」把「prompt 改完效果会不会变」这个所有 LLM 工具都回避的问题正面解决，是全项目可迁移性最高的资产
  • 把幻觉关进契约里：「零发现」在失败扫描中等于不可判定而非安全、报告只是 canonical JSON 的确定性投影而非模型输入、Finding 身份由机器派生而非模型自称——这是一套完整的「AI 产物可信化」答案

作者视角：为什么存在这个项目

创始人/作者背景

OpenAI 官方组织账号（11.1 年建号，278 个公开仓库，143,364 粉丝），主作者 mldangelo-oai 单人贡献 57.2% 的 commit（1,245 次）。项目前身是 2025 年 10 月内部私有测试的 Aardvark，2026 年 3 月 6 日以 research preview 形式发布，2026 年 7 月 29 日以 Apache-2.0 开源 CLI 与 SDK——从内部产品到开源产品只用了 9 个月，是 OpenAI 罕见的「产品即开源」路径。

一个容易被忽略的背景信号：仓库贡献者榜第二位是 Codex 这个 AI agent 身份（440 次 commit）。这个仓库本身就是「主要由 agent 参与开发」这一事实的公开证据，这直接决定了后面会讲到的 AGENTS.md 写法。

问题判断

作者看到的是「扫描到修复之间的断层」，而不是「扫描能力不足」。四个具体缺口：

  1. 扫描器发现没有上下文——Semgrep 告诉你第 427 行有路径穿越，但不告诉你这条路径在当前架构下能不能被外部触达
  2. 误报判定没有证据标准——AGENTS.md 里写着「A control's name... alone does not settle the claim」，控制点名字本身不能证明问题不存在
  3. 修复闭环断裂——verify-fix 保留了 inconclusive 第三态，而不是只有「修好了/没修好」两个答案
  4. 非确定性 agent 无法回归——传统 CI 断言不了「这个 prompt 改完还能不能发现那个漏洞」

时机为什么是现在：Codex agent 本身的成熟度刚好越过「能跑复杂多步任务」的门槛，同时 LLM 驱动的 SAST 在 2026 年集体进入工程化阶段（Anthropic 4 月公测 Claude Code Security、AWS Continuum 同年入场）。但 OpenAI 做了 Anthropic 没做的一步：把契约、评测、失败模式全部公开。

解法哲学

AGENTS.md 全篇 155 行是「什么不要写」，这比任何 feature list 都更能说明作者的世界观。三条最反直觉的纪律：

  • 主动拒绝凭据脱敏：理由是脱敏会破坏可信度且不可验证，防护应该放在发布环节而不是本地诊断环节
  • 不维护 wrapper 自有的 model 枚举：模型能力从上游发现，避免「模型已发布但枚举没更新」这种滞后
  • CLI 表面视为公开 API：禁止随手加 flag——CLI 是 agent 的调用界面，改动等于破坏契约

同时明确不做什么：不做 SCA、不做 IaC、不做 Secrets 扫描（这三块交给 Snyk/Trivy/Wiz/GitHub 三件套，Codex Security 提供的是导入它们发现的通道）。这个「不做清单」比它的功能列表更能说明战略。

战略意图

基础设施，而非核心产品；open-core，而非 genuinely open。 开源部分：CLI + TypeScript SDK + 20 个 skill + 17 家扫描器导入 + 全部契约文档。封闭部分：Codex Security Cloud（findings 集中管理）、Daybreak 分级准入、以及背后的模型额度。定价至今未公开。

更深的战略是把开源 CLI/SDK 当作漏斗顶端：让工程师在本地免费跑通扫描产生信任，把 findings 管理、跨仓库整改、Daybreak 深度扫描这些高价值场景留在 Cloud。

核心价值提炼

创新之处

  1. Sealed Scan Contract——把 AI 产物变成可审计的不可变收据（新颖度 4/5 | 实用性 5/5 | 可迁移性 5/5）
    scan-manifest.json 记录 scanId/target/scope/status/sealTime 与每个 artifact 的 SHA-256，manifest 记录摘要但不自哈希（避免自引用）；report.md 是从 canonical JSON 确定性投影出来的下游产物而非模型输入——「Producers must not author report.md」。模型无法通过写一份漂亮的报告来掩盖证据不足。

  2. 语义化 Finding 身份：findingId 跨扫描稳定，occurrenceId 单次唯一（新颖度 4/5 | 实用性 5/5 | 可迁移性 5/5）

    material = "\0".join(("codex-security/v1", target_id, rule_id, anchor, instance))
fingerprint = "codex-security/v1:sha256:" + sha256(material)
findingId    = "csf_" + sha256(fingerprint)[:24]     # 同一漏洞始终是同一个
occurrenceId = "occ_" + sha256(scan_id + fingerprint)[:24]  # 第 N 次扫描里的第 N 个实例

    代码在 review 之间会移动、改名、拆行，基于 file:line 的指纹必然失效——「同一个漏洞在第 3 次扫描时变成新漏洞」。而 finalizer 强制校验而非修复：身份冲突直接报 ContractError。模型提供语义，机器提供身份。

  3. agent 评测的「布局分离 + 三信号分离 + 原始分保留」（新颖度 5/5 | 实用性 5/5 | 可迁移性 5/5）
    评测 README 里主动声明：「This is layout separation, not a filesystem security boundary.」——作者不夸大隔离强度。同时把 safe-control overlap / unmatched finding / citation error 三类问题分开记账而非合并成一个精确率，并保留原始分、单独记录人工裁决。

  4. 「零发现」在非 completed 状态 = 不可判定，不是安全（新颖度 4/5 | 实用性 5/5 | 可迁移性 5/5）
    契约明确四态（completed/failed/canceled/interrupted），只有 completed 支持完成结论，其余状态必须保留已发现项并把「没有发现」视为 inconclusive。这是很多工具做错的那一格。

  5. Protected Root 双向排除 + 双层强制（新颖度 4/5 | 实用性 4/5 | 可迁移性 5/5）
    字符串层查一次、realpath 解析 symlink 后再查一次——单层会被 symlink 绕过。且排除是双向的：输出目录不能落在仓库内，仓库也不能落在输出目录内（否则输出目录里的其他项目也在写入范围）。

  6. 「软时间预算」而非硬超时（新颖度 4/5 | 实用性 4/5 | 可迁移性 4/5）
    硬超时会在关键推理中途砍断产出半成品；软约束则被模型忽略。解法是跨 worker 共享绝对 deadline + 明令禁止 padding + finalization 阶段在预算之外。这是「预算语义进 prompt、成本闸门留给硬校验」的分工。

  7. 生产 prompt 本身即被测对象（新颖度 4/5 | 实用性 5/5 | 可迁移性 5/5）
    secret-discovery 评测直接测生产环境用的 prompt：不给模型任何 hint，grade 严格检查 CWE + 分类 + 精确位置 + codeEvidence 覆盖。多数团队只测「skill 能不能跑通」，这里测的是「prompt 变体 A 和 B 的发现率差异」。

  8. check-skills：用安全扫描器审 agent skill 本身（新颖度 5/5 | 实用性 3/5 | 可迁移性 4/5）
    把 prompt injection / 数据外泄 / 越权工具调用这类检查反向应用到 20 个 skill 自身——agent 的「代码」就是 prompt 文本，而 prompt 同样可以是攻击面。

  9. 扫描器导入的「身份归一表」（新颖度 3/5 | 实用性 4/5 | 可迁移性 4/5）
    17 家厂商的 finding ID 语义各不相同，Codex Security 显式建了一张归一映射表，而不是让各家 ID 直接混在一张表里。

  10. SARIF 作为有损投影且明示损失（新颖度 3/5 | 实用性 5/5 | 可迁移性 5/5）
    「Lifecycle, rich validation evidence, attack-path context, and coverage are lossy or omitted in SARIF.」同时把语义指纹保留在 codexSecurity/v1 自定义属性下，让跨系统去重仍然可行。

关键设计决策

  1. 决策：Finding 用语义身份而非位置身份

    • 问题：代码在 review 之间会移动、改名、拆行，file:line 指纹必然失效，去重失效 → 趋势失真 → 工单爆炸
    • 方案：identity.anchor（语义化 root-control 锚点，不含行号）+ identity.instance（同 rule+anchor 下可独立攻击的兄弟实例），两级哈希派生 findingId / occurrenceId
    • Trade-off：牺牲了精确到行的可追溯性——两个 anchor 相同但位置完全不同的漏洞必须由模型用 identity.instance 显式区分，否则 finalization 直接报错。换来跨扫描稳定去重
    • 可迁移性：高

  2. 决策：Protected Root 与 Output Directory 双向排除 + SDK/CLI 双层强制

    • 问题：agent 扫描时写文件（report.md、findings、evidence）。输出目录落在被扫描仓库里 → 扫描器把自己的产物当待审代码 → 既污染下轮扫描又可能造成自我提示注入
    • 方案：字符串层 + realpath 层各查一次（runtime.ts:1925-1950 的 requireOutputOutsideRepository）；api.ts:890-940 在 canonical 化前后各强制一次
    • Trade-off：用户不能把结果直接输出到仓库内（README 明确「saves its draft outside the repository and leaves existing files unchanged」）。这是刻意的
    • 可迁移性：高——代码修复 agent、文档生成 agent 都需要这层

  3. 决策：封存扫描契约（Sealed Scan Contract）而非快照

    • 问题：扫描结束后结果可能被重新 finalization、修补、重新导出。结果会变，下游（CI 门禁、工单系统、趋势分析）就无法信任
    • 方案：manifest 记摘要不自哈希；report.md 由 Python finalizer 确定性投影生成，模型无权写；契约文档还划清了存储边界——「This bundle records immutable scan observations. It is not a workflow-state database.」
    • Trade-off：不能就地修改扫描结果（改一个 finding 的状态要去别处）；换来可审计性 + 可重生成性
    • 可迁移性：高

  4. 决策：把时间预算做成 prompt 策略而非硬超时

    • 问题：issue #25——第三方实测单次扫描 $1.64 到 $55。硬超时砍断关键推理产出半成品，软约束被模型忽略
    • 方案：跨 worker 共享绝对 deadline、prompt 明写「advisory, not a hard timeout or minimum runtime」、禁 padding、finalization 在预算外；硬成本闸门另行承担
    • Trade-off：用户仍无法预测单次成本（预算语义没做 scope 预览，官方至今未解）
    • 可迁移性：中高

  5. 决策：20 个 skill 用「负向边界」契约定义

    • 每个 skill 都有 Do not use for X 段落，而不是只说「能做什么」。这让 agent 在能力边界上不会误用（比如用 threat-model 去回答具体漏洞是否存在）
    • Trade-off：维护成本更高；换来 agent 路由的确定性——workflow-routing 评测专门验证「自然语言请求是否路由到正确 skill」，要求真实 shell-tool trace 读到正确 skill 的标题
    • 可迁移性：高

  6. 决策：evals 五层递进给非确定性 agent 造确定性回归

    • triage-finding（Promptfoo + JSON schema 断言）/ calibration（成对 commit：vulnerable vs fixed，标签留在模型读不到的目录外）/ sastbench（外部基准）/ secret-discovery（生产 prompt 能否发现合成凭据）/ standard-time-budget（有/无 maxTimeMinutes 的配对 A/B 实验）/ workflow-routing（隔离 HOME 禁用 ambient skill）
    • Trade-off：评测套件本身很重，CI 只跑确定性部分（node --test evals/*/test_*.mts），model-backed 部分 opt-in——大部分 agent 行为变更在 CI 里不可见，这是 LLM 产品的结构性困境
    • 可迁移性：最高

  7. 决策：超大文件的组织方式——诚实评估技术债

    • 事实：cli.ts 13,714 行改 336 次（平均每 11 个工作日一次）、api.ts 7,847 行改 218 次、runtime.ts 4,826 行改 137 次
    • 正面：incur + Zod schema 定义命令 → 命令 schema 就是 --schema --format json 的输出源 → CLI 自描述、可被另一个 agent 安全驱动
    • 负面：13,714 行单文件是明显的合并冲突热点，任何 refactor 都是高风险
    • 缓解：周边确实在拆（cli-help.ts / cli-integrations.ts / cli-mcp.ts / cli-signals.ts / cli-token-view.ts）
    • 未解：核心逻辑仍在 cli.ts 里

差异化护城河

  • 信任护城河（最强）：闭源竞品无法提供同等可审计性——20 份 reference 契约 + 封存产物 + 开放源码，让「我们凭什么说这是漏洞」这个问题能被第三方独立核查
  • 生态护城河（次强）：17 家扫描器导入 + 统一 finding 身份 → 它在做分诊层而非扫描层，这是竞品都没有占的位置
  • 技术护城河（最弱）：LLM 编排本身在商品化，Claude Code Security 架构更同构且模型更强

竞争风险

最大风险来自 Claude Code Security——同为 LLM 主引擎 + 多阶段自验证，Anthropic 模型能力更强、品牌更硬。但它不开源、仅 Enterprise 可用，在「CI 集成完整度 + 17 家扫描器导入 + 多 provider（OpenAI/Bedrock/OpenRouter/Fireworks）」上仍有差距。

次级风险是成本劣势：Semgrep 便宜 1-2 个数量级且可完全离线，这决定了在合规审计、确定性要求高的场景里 Semgrep 仍会赢。此外产品自身的治理反讽——社区记录 Codex Security 曾有 GitHub token 泄露型分支命令注入漏洞（2025-12 报告、2026-02 修复，51 天窗口），且无公布 SLA。

生态定位

「安全工具链的分诊层 + 编排层」——不与 Semgrep 抢扫描能力，而是把 20+ 个扫描器的发现统一进一个上下文感知的 triage agent，再驱动 fix/verify 闭环。这个位置目前没有别人占，但也可能没有别人愿意占（因为它需要同时理解扫描器语义和 agent 编排）。

套利机会分析

  • 信息差：流量层面没有套利空间——13,276 star、HN 首页 392 分，热点已充分反映。真正稀缺的是源码里的工程范式：evals 五套评测、scan-contract.md 的 canonical schema、Protected Root/Output Directory 隔离模型，都是能直接抄进自己项目的资产

  • 技术借鉴：

    • 「模型给语义、机器给身份」——任何做 AI 扫描/审计/代码修复的产品都能直接抄，成本极低收益极高
    • evals 套件的布局分离与三信号分离——这是目前公开可见的、对非确定性 agent 做回归的最完整方案
    • AGENTS.md 的「什么不要写」写法——本项目最被低估的单文件资产，任何 AI 参与开发的项目都能抄
    • 报告是投影不是源——这条可以直接套到任何「让模型输出报告」的系统上，杜绝模型粉饰
  • 生态位：填补的是「多扫描器发现 → 上下文感知分诊 → 修复验证」这条链路，目前生态里没有第二家开源方案
  • 趋势判断：2026 年是 LLM 安全工具集体入场年（OpenAI/Anthropic/AWS 三家同年），codex-security 没有后发优势，但有唯一的「全开源」优势。随着 agent 安全从玩具走向企业采购，契约与评测的稀缺性会超过扫描能力本身的稀缺性——这是它的长期位置

风险与不足

  1. 成本不可预测：官方至今未提供 scope 预览与预算语义，issue #25 仍是未解状态；实测单次 $1.64–$55 的方差对企业采购是硬伤
  2. 非确定性与合规冲突：SOC 2 / PCI-DSS / FedRAMP 场景要求可复现的检测逻辑，而 LLM 输出不可复现——这恰恰是 Semgrep 在治理场景赢的地方
  3. 必须上传源码至 OpenAI 云端：私有仓库无法全本地扫描，这在中国/欧盟的合规环境下可能是硬门槛
  4. 巨型单文件技术债：13,714 行 cli.ts / 7,847 行 api.ts，平均 11 个工作日改一次，refactor 风险高
  5. 注释率仅 4.2%：对 54 万行代码偏低，虽然契约文档层补足了这部分语义，但源码内的「为什么」容易丢失
  6. Agent 行为变更在 CI 里大部分不可见：model-backed evals 是 opt-in，意味着「改 prompt 改坏了」要到线上才暴露
  7. 产品自身的安全反讽：曾曝出 51 天才修复的命令注入漏洞；社区还记录到「候选发现因 evidence ID 畸形被整体丢弃、最终零可报告发现」的案例
  8. star 层面已透支：3.5 个月内从 1.5k 涨到 13.3k，评分与关注度压力会持续影响 maintainer 节奏（近 30 天 955 次 commit 印证了这一点）

行动建议

如果你要用它

  • 选它的场景：逻辑漏洞 / 业务流漏洞 / 需要修复闭环而非只要一份 finding 列表；已有多个扫描器需要一个统一分诊层；团队能接受单次 $2–$50 的模型成本
  • 别选它的场景：合规审计要求可复现规则（选 Semgrep）；需要 SCA/IaC/Secrets（选 Snyk 或 GitHub 三件套）；无法接受源码上云；预算敏感且规模大（Semgrep 便宜 1-2 个数量级）
  • 部署建议：先用 import 通道接已有的 Semgrep/Snyk/Trivy 发现喂给 Codex Security 做 triage（成本最低、收益最快），再考虑启用它自己的扫描能力

如果你要学它

必读五个文件，按信息密度排序：

  1. plugins/codex-security/references/scan-contract.md（192 行）——全项目最高信息密度：finding identity、seal 语义、状态语义
  2. AGENTS.md（155 行）——「什么不要写」的工程价值观模板，可直接复制到任何 AI 参与开发的项目
  3. evals/standard-time-budget/README.md + evals/triage-finding/README.md——非确定性 agent 回归评测的完整方法论
  4. sdk/typescript/src/runtime.ts:1925-1990 与 src/api.ts:890-940——路径隔离的字符串层 + realpath 层双强制实现
  5. plugins/codex-security/scripts/finalize_scan_contract.py:1036-1130——指纹派生与身份覆写的 fail-fast 实现

如果你要 fork 它

  • 不要碰 cli.ts——13,714 行、336 次改动，任何 refactor 的收益都低于风险；用 Zod schema 在外围加命令而不是拆核心
  • 优先补的是 scope 预览（对应 issue #25）：这是所有用户的第一诉求，且是纯增量功能，不需要改动契约层
  • 可摘出去复用的模块：sdk/typescript/src/deduplication/（13 模块 2,726 行）、sdk/typescript/src/provider-profile.ts（254 行，多 provider 凭据不进 argv）、evals/ 五套评测——这三个几乎不依赖 OpenAI 特定的东西
  • 注意 open-core 边界：Cloud 托管路径在 src/hosted-*.ts（约 6 个文件），fork 时需要决定是否剥离
